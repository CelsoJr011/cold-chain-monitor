## Why I built this

I work in operations at a distribution center that ships medicines to pharmacies. Some of those products — insulin is the classic example — have to travel between **2 and 8 °C**. They go out in thermal boxes with ice packs and a small **temperature logger** inside, which records a reading every few minutes.

When the box comes back, someone has to look at that log and answer one question: *did the product stay in range?* Most days the answer is an easy yes. The hard days are the ones with a spike at 9 °C during a delivery, a truck stuck in traffic in the afternoon, an ice pack that froze the products, or a logger that simply stopped recording for half an hour.

My previous project ([fefo-pharma-stock](https://github.com/CelsoJr011/fefo-pharma-stock)) had "temperature log for cold chain batches" in its next steps list, so this is that idea as its own tool: open the log, see the chart, see the excursions, and get a verdict **with the reasons written out**.

> ⚠️ All routes, boxes, shipments and readings here are **fictional** and generated by code. The limits and tolerances are **demo values I chose** — in real life they come from each product's stability data and from the quality team's procedures.

## Features

**Overview**
- Summary cards: shipments, approved, needs review, quarantine, number of excursions and average time in range
- Shipment list sorted **worst first** (quarantine → review → approved), with route, box, departure, duration and min/max
- Filter by verdict

**Shipment detail**
- Temperature chart drawn in SVG: the 2–8 °C band, the hard limits as dashed lines and every out-of-range reading in red
- The line is broken where the logger stopped recording, instead of drawing fake readings across the gap
- Lowest, highest and average temperature, time in range, time out of range, number of readings
- **Why this verdict** — one sentence per reason, with the numbers — and **what to do** next
- Table of excursions (too warm / too cold, from, to, duration, peak) and list of gaps in the data

**Import a logger file**
- Upload a CSV or paste the readings
- Works with the Brazilian format (`;` and decimal comma: `4,5`) and the international one (`,` and decimal point: `4.5`), with or without a header line
- Shows the problems **with the line number** (bad date, temperature that isn't a number, missing column)
- "Fill with an example" button to try it without a file
- Imported shipments are saved in the browser (`localStorage`) and can be removed

**Three languages: 🇺🇸 EN · 🇧🇷 PT · 🇫🇷 FR**
- Buttons in the header switch everything: labels, verdicts, reasons, error messages, durations, the sample route names, the page `<title>` and the `lang` attribute
- Numbers, dates and times follow the language (`4.5 °C` in English, `4,5 °C` in Portuguese and French; `87,5 %` with the French space)
- The choice is remembered; on the first visit the app follows the browser language (English if it's none of the three)
- Switching language keeps what you were looking at: selected shipment, filter, chosen file and the last import message

**Other**
- Responsive layout (the chart is redrawn at the real width of the screen)
- Unit tests for the rules, the CSV parser and the translations

## How it works

### 1. Each reading: in range or not

A reading is **ok** between 2 and 8 °C (both included), **high** above 8 and **low** below 2.

### 2. Excursions

An excursion is a run of readings in a row outside the range, in the same direction. The interesting part is the **duration**.

The logger only records every 5 minutes (or 10, or 15), so I don't know the exact minute the box went above 8 °C. I chose the **worst case**: the excursion starts at the last good reading *before* the run and ends at the first good reading *after* it.

```
08:00  5.1 °C
08:05  6.0 °C   ← last good reading  → excursion starts here
08:10  8.5 °C   ✗
08:15  9.2 °C   ✗
08:20  7.0 °C   ← first good reading → excursion ends here
                   duration: 15 min, peak: 9.2 °C
```

Two readings out of range, but 15 minutes counted. A quality team would rather overestimate an excursion than underestimate it, so the code does the same. If the log ends while still out of range, the excursion is marked as **still open**.

### 3. Gaps in the data

The interval between readings is taken from the file itself, using the **median** (one or two weird gaps don't change it, an average would). Any gap bigger than **2× that interval** is reported.

A gap is not an excursion — every reading can be perfect — but **no data means no proof**. So it sends the shipment to review.

### 4. The verdict

| Verdict | When | What to do |
|---|---|---|
| 🔴 **Quarantine** | any reading **≤ 0 °C** (may have frozen), any reading **above 12 °C**, or **more than 60 min** out of range in total | Keep the products apart until the quality team analyses them |
| 🟠 **Needs review** | left the range but within the tolerance, or the logger has gaps | Send the report to the quality team before releasing |
| 🟢 **Approved** | every reading between 2 and 8 °C, no gaps | Release as usual |

Freezing is checked first on purpose: for many refrigerated products, getting too cold is worse than a short warm spike.

All these numbers live in one object, `DEFAULT_RULES` in `js/monitor.js`, and every function accepts other rules — the tests use a 15–25 °C range to make sure nothing is hard-coded to 2–8.

### 5. The sample shipments

The five sample shipments each tell a small story, and they're generated by code (two sine waves for the normal swing of a box, plus an "event"):

| Shipment | What happened | Verdict |
|---|---|---|
| RT-101 | Nothing — a normal day | Approved |
| RT-102 | Box left open at a delivery, spike to 9.3 °C for 25 min | Needs review |
| RT-103 | Truck stuck in afternoon traffic, up to 13.5 °C for 1 h 50 min | Quarantine |
| RT-104 | Frozen ice pack against the products, down to −0.4 °C | Quarantine |
| RT-105 | Temperature fine, but the logger stopped for 50 min | Needs review |

They always happen "yesterday", so the demo never looks old.

### 6. Translations

I speak Portuguese, English and French, so the tool works in all three. Every text comes from `js/i18n.js`, one dictionary per language, with `{placeholders}` for the numbers:

```js
translate('pt', 'import.success', { id: 'RT-201', n: 30 }); // "Carga RT-201 importada com 30 leituras."
translate('fr', 'import.errorLine', { line: 4, reason: '…' }); // "Ligne 4 : …"
```

A few details:
- A missing key falls back to English, then to the key itself, so the screen never breaks.
- Two tests protect the translations: PT and FR must have **the same keys** as EN, and **the same placeholders** (a translation that forgets `{n}` would hide the number that matters).
- The rules and the CSV parser never return sentences, only codes (`'freeze'`, `'gap'`, `{ line: 3, reason: 'date' }`). The screen turns them into text in the chosen language.
- The native file button shows its text in the *browser's* language, so it's hidden and replaced by a translated one.
- Routes typed by the user stay as typed — free text can't be translated reliably.
- I used the Canadian locales (`en-CA`, `fr-CA`) for numbers and dates; that's why French times show as `14 h 40`.

## Technical decisions

- **Rules separated from the screen.** `js/monitor.js` and `js/csv.js` have no DOM code, so they run in the browser and in Node. That's what made the tests easy.
- **Hand-made SVG chart instead of a library.** I used Chart.js in [helpdesk-lite](https://github.com/CelsoJr011/helpdesk-lite). Here I needed a colored band, dashed limit lines, red dots and a line that breaks on gaps — drawing that in SVG was less code than bending a library to do it.
- **Timestamps without time zone.** A logger in a truck in Brazil records local time, and `"2026-11-21T14:40"` (no `Z`) is read by JavaScript as local time. The sample data is built with a local formatter on purpose — `toISOString()` would shift every trip by 3 hours. Tests run fine with `TZ=UTC`, `TZ=America/Sao_Paulo` and `TZ=Europe/Paris`.
- **Only imported shipments are saved.** The samples are rebuilt on every visit, so their dates stay fresh.
- **Escaping user input.** IDs, routes and box names typed in the form go through `escapeHtml` before being shown.
- **No framework.** For one screen, vanilla JS keeps the logic visible. If this grew (users, history, several warehouses), React + TypeScript would be the next step.

## Running locally

The app uses ES modules, so it needs to be served (opening `index.html` straight from the file system won't load the scripts).

```bash
git clone https://github.com/CelsoJr011/cold-chain-monitor.git
cd cold-chain-monitor

# any static server works
python3 -m http.server 8000
# or
npx serve .
```

Then open **http://localhost:8000**.

### Running the tests

Requires Node.js 18+ (nothing to install):

```bash
npm test
```

### Trying the import with your own file

Any CSV with date/time in the first column and temperature in the second:

```
Data/Hora;Temperatura (°C)
2026-11-22 07:00;5,0
2026-11-22 07:10;5,3
2026-11-22 07:20;8,7
2026-11-22 07:30;5,6
```

## What I learned

- "How long was it out of range?" has more than one correct answer when you only have a reading every 5 minutes. Choosing the worst case — and writing down why — mattered more than the code itself.
- Missing data is its own kind of problem. In RT-105 every reading is perfect, and it still can't be approved: for 50 minutes nobody knows what happened inside the box.
- Returning codes instead of sentences from the rules made the translations much simpler: the logic doesn't know which language is on the screen.
- Drawing a chart by hand teaches you what a chart library does for you (scales, ticks, responsive width).
